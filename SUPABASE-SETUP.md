# Supabase setup

This project uses Supabase for accounts, messages, player world seeds, and discovered messages. Create and configure the project yourself in the Supabase dashboard. The game will use only the public project URL and publishable key in the browser; never put a database password, service-role key, or secret key in the app.

## 1. Create the project

1. Open [Supabase Dashboard](https://supabase.com/dashboard), sign in, and choose **New project**.
2. Select your organization, enter a project name, choose a region, and create a strong database password. Keep the password private; the game does not need it.
3. Wait until the project has finished provisioning.

## 2. Enable email sign-in

1. In the project, open **Authentication → Providers → Email** and enable email authentication.
2. Choose whether email confirmation is required. When it is enabled, a new account must confirm its email before signing in.
3. In **Authentication → URL Configuration**, set the Site URL to the app URL you use. For local development, use `http://localhost:5173`.
4. Add the local development redirect URL `http://localhost:5173/**`. Add your deployed app URL and its allowed redirect path here when you deploy.

## 3. Create the tables and security policies

Open **SQL Editor → New query**, paste the complete SQL below, review it, then click **Run** yourself. It creates the message, profile, and achievement tables and their row-level security rules. The grants limit achievement updates to the `read_at` column; the client cannot update discovery timestamps or message ownership through a normal table update.

```sql
create table if not exists public.messages (
  id bigint generated by default as identity primary key,
  text text not null check (length(btrim(text)) > 0),
  is_active boolean not null default true,
  created_at timestamptz not null default now()
);

create table if not exists public.player_profiles (
  user_id uuid primary key references auth.users(id) on delete cascade,
  world_seed bigint not null check (world_seed between 0 and 4294967295),
  created_at timestamptz not null default now()
);

create table if not exists public.player_achievements (
  user_id uuid not null references auth.users(id) on delete cascade,
  message_id bigint not null references public.messages(id) on delete cascade,
  discovered_at timestamptz not null default now(),
  read_at timestamptz,
  primary key (user_id, message_id)
);

create index if not exists player_achievements_order_idx
  on public.player_achievements (user_id, discovered_at, message_id);

alter table public.messages enable row level security;
alter table public.player_profiles enable row level security;
alter table public.player_achievements enable row level security;

create policy "Authenticated users read active messages"
  on public.messages for select to authenticated
  using (is_active = true);

create policy "Players read own profile"
  on public.player_profiles for select to authenticated
  using ((select auth.uid()) = user_id);
create policy "Players create own profile"
  on public.player_profiles for insert to authenticated
  with check ((select auth.uid()) = user_id);

create policy "Players read own achievements"
  on public.player_achievements for select to authenticated
  using ((select auth.uid()) = user_id);
create policy "Players unlock own achievements"
  on public.player_achievements for insert to authenticated
  with check ((select auth.uid()) = user_id and read_at is null);
create policy "Players mark own achievements read"
  on public.player_achievements for update to authenticated
  using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);

revoke all on public.messages, public.player_profiles, public.player_achievements
  from anon, authenticated;
grant select on public.messages to authenticated;
grant select, insert on public.player_profiles to authenticated;
grant select, insert on public.player_achievements to authenticated;
grant update (read_at) on public.player_achievements to authenticated;
```

The app submits an unlock when a player reaches a board. As the addendum explains, this client-side rule is not cheat-proof: a determined authenticated user could submit an unlock request without visiting the board. A server-validated RPC would be needed to prevent that. This setup does keep each user's rows private from other users and prevents anonymous access.

### Enable completed-progress reset

Open **SQL Editor → New query**, paste the contents of [`SUPABASE-RESET-ACHIEVEMENTS.sql`](./SUPABASE-RESET-ACHIEVEMENTS.sql), and run it once. It adds an authenticated RPC that refuses to reset until all active messages are found, then deletes only the signed-in player's achievement rows. The game shows the reset button only after completion and asks for confirmation. The player's world seed is preserved.

## 4. Add messages

Open **Table Editor → messages → Insert row** and add message rows yourself. Leave `id` and `created_at` empty so the database fills them in. Enter the message in `text` and set `is_active` to `true`. Unicode Vietnamese text and newlines are supported. You can also import a CSV through the dashboard. Start with approximately 50 messages; the game will use the active row count rather than assuming there are exactly 50. Keep message text around 280 characters so it fits comfortably on a board.

The `messages` table is the runtime source of message text. Do not add message copies to the source tree or browser storage. Manage message edits and activation from the dashboard.

## 5. Add the public app credentials locally

In **Project Settings → API** (or the dashboard's current API settings page), copy the **Project URL** and **publishable key**. A legacy `anon` key may be used if the project only shows that key. In the project root, create a local `.env` file:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

Replace both values with your project's public values. Keep `.env` local and out of version control. Never use `service_role`, secret, or database password values in these variables. Restart the Vite development server after adding or changing `.env`.

## 6. Verify setup after the game integration is ready

The login screen and database integration are added in the next milestone, so this check is for after that work is complete:

1. Create an account through the game's sign-up screen and confirm the email if required.
2. Sign in and check that active messages load.
3. Discover a board, refresh, and confirm the progress remains.
4. Sign in on a second browser/device and confirm the same account sees the same board placement and progress.
5. Sign out and confirm the next account does not see the previous account's in-memory messages or progress.

Do not send anyone a database password or secret key. To continue with live integration testing, confirm that you completed the dashboard setup and added the local public credentials; do not paste the key into chat.
