# SPEC Addendum — Message boards, achievements and stamina

Adds three features to the finished base game, with Supabase-backed accounts and persistence:
1. **Message boards** scattered through the world, one per message (50 by default).
2. **Achievements**: walking into a board's chunk unlocks its message, plays a chime, and stores it in a readable log.
3. **Stamina** (sức bền): galloping drains it, eating refills it.

Do the milestones in section 9 in order. The world, grass chunks, horse controller, auto-wander and audio manager already exist; reuse them, do not rebuild them.

> **Design note.** The board in the reference screenshot is from another game, with that author's name ("BÒ TV") and a donation QR code. Build our own board design and use our own wording and artwork. Do not copy that name, QR code or layout text.

## 1. Supabase setup, authentication, and message data

### 1.1 Mandatory manual setup boundary

**The developer/AI implementing this spec MUST instruct the user to create and configure Supabase manually on the Supabase website. Do NOT create a Supabase project, run migrations against the user’s project, create tables, configure authentication, add messages, or change policies on the user's behalf.** Provide the user with copyable SQL and clear step-by-step website instructions, then wait for confirmation that setup is complete before testing live database integration. Do not ask for a database password or service-role/secret key. The app may use the public project URL and publishable/anon key only; never put privileged keys in frontend code.

Instructions to give the user:
1. Visit https://supabase.com/dashboard, sign in, select **New project**, choose organization/name/region and a strong database password, and wait for provisioning.
2. In **Authentication → Providers**, enable Email authentication; choose email confirmation settings (if enabled, users must confirm before signing in). Configure the app's Site URL and permitted redirect URLs as appropriate.
3. Open **SQL Editor**, paste the SQL in section 1.2, review it, and click **Run** themselves. This creates the required tables, constraints, indexes and row-level security policies.
4. In **Table Editor**, insert and edit message rows in `public.messages` themselves (or use the Supabase CSV import UI). Do not add messages to source code. `text` is Unicode and supports Vietnamese/newlines. Add approximately 50 rows initially, but the count is dynamic.
5. In **Project Settings → API** (or the current Supabase dashboard equivalent), copy the project URL and **publishable key** (or legacy anon key) into local `.env` values `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`. Restart the development server. Do not commit `.env`.
6. Create a test account using the game's sign-up screen, log in, verify the messages load, and test progress after refresh and on a second browser/device.

### 1.2 SQL to supply to the user (user runs manually)

```sql
create table if not exists public.messages (
  id bigint generated by default as identity primary key,
  text text not null check (length(btrim(text)) > 0),
  is_active boolean not null default true,
  created_at timestamptz not null default now()
);

create table if not exists public.player_profiles (
  user_id uuid primary key references auth.users(id) on delete cascade,
  world_seed bigint not null check (world_seed between 0 and 4294967295),
  created_at timestamptz not null default now()
);

create table if not exists public.player_achievements (
  user_id uuid not null references auth.users(id) on delete cascade,
  message_id bigint not null references public.messages(id) on delete cascade,
  discovered_at timestamptz not null default now(),
  read_at timestamptz,
  primary key (user_id, message_id)
);
create index if not exists player_achievements_order_idx
  on public.player_achievements (user_id, discovered_at, message_id);

alter table public.messages enable row level security;
alter table public.player_profiles enable row level security;
alter table public.player_achievements enable row level security;

create policy "Authenticated users read active messages"
  on public.messages for select to authenticated
  using (is_active = true);

create policy "Players read own profile"
  on public.player_profiles for select to authenticated
  using ((select auth.uid()) = user_id);
create policy "Players create own profile"
  on public.player_profiles for insert to authenticated
  with check ((select auth.uid()) = user_id);

create policy "Players read own achievements"
  on public.player_achievements for select to authenticated
  using ((select auth.uid()) = user_id);
create policy "Players unlock own achievements"
  on public.player_achievements for insert to authenticated
  with check ((select auth.uid()) = user_id and read_at is null);
create policy "Players mark own achievements read"
  on public.player_achievements for update to authenticated
  using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);
```

**Production hardening:** The basic client-side unlock mechanism trusts the authenticated player to submit an unlock. If cheating resistance matters, replace direct inserts with a server-validated unlock endpoint/RPC and restrict direct insert/update policies. The `read_at` update policy above permits editing other achievement columns through a custom client; for stronger integrity, use a dedicated `mark_read` RPC and revoke direct updates. Admin-only message creation/editing is done manually in the Supabase dashboard; do not add client insert/update/delete policies on `messages`.

### 1.3 Source of truth and loading

- Supabase `public.messages` is the **only runtime source of message text**. Do not use `messages.json`, hard-coded strings containing message content, `localStorage`, `sessionStorage`, IndexedDB, or browser caches for game data.
- On authenticated startup, fetch all active messages, ordered by `id` (handle Supabase pagination; never assume the default row limit covers all messages). Validate unique ids and nonempty text, report bad records, and use valid records only.
- Stable database `id` identifies a message even if its text changes. Do not use array positions as identities. Board placement and achievement lookup must use these stable ids.
- The total board count comes from the returned active messages, not a hard-coded 50. When the set of active message ids changes, recompute deterministic placement from the stable sorted ids; existing unlocked achievements remain tied to message ids. Warn that adding/removing messages can shift board positions under the specified shuffle algorithm; for immovable placements, add a dedicated persisted placement table in a future version.
- Recommended board text length is approximately 280 characters; the achievement panel shows the full text. A message edit in Supabase appears after the next fetch/reload, including for previously unlocked messages.
- Never allow unauthenticated play to silently create local-only achievements. Show login or a clearly labeled retry/error state if Supabase cannot be reached.

### 1.4 Basic authentication and per-user persistence

- Use `@supabase/supabase-js` and Supabase Auth for **email/password sign-up, sign-in, sign-out**, session restoration and auth state changes. Include a simple accessible login screen with loading/error states and a password field; do not implement your own password storage.
- On first authenticated login, generate a cryptographically random unsigned 32-bit `world_seed` with `crypto.getRandomValues`, then `upsert` the profile with `onConflict: 'user_id'` and `ignoreDuplicates: true`; select the stored row afterward. Never overwrite an existing seed. If two devices initialize simultaneously, the database row wins.
- Supabase Auth SDK may maintain its own authentication session using its supported persistence mechanism. **This is the sole exception** to the no-browser-storage rule, and is for auth tokens only, never messages, world seeds or achievements. If absolutely no browser persistence of any kind is allowed, configure `persistSession: false` and require login after refresh.
- Fetch achievements filtered to the authenticated user (RLS enforces this even if the client filter is wrong). On sign-out or account switch, immediately clear in-memory messages, progress, textures, and profile data; then load the new user's data.
- Never use the Supabase service-role/secret key in the browser. Do not store passwords in the app database. All data operations must respect RLS.

## 2. Where boards go (placement)

**Interpretation to confirm with the user:** boards are placed so that **neighbouring boards are about 30–40 chunks apart**, and the first boards are 30–40 chunks from the spawn point. If the user meant something else, only the constants below change.

### 2.1 Algorithm (deterministic, no storage needed)
Use the game's own **chunk** coordinates (the same grid used by the grass system). Constants in `src/config/boards.ts`:

```ts
export const BOARD_CELL = 35;      // chunks per cell. Allowed range 30-40
export const BOARD_JITTER = 2;     // +-2 chunks random shift inside the cell
export const BOARD_LOAD_RADIUS = 10; // chunks: create the board mesh when the player is this close
export const BOARD_UNLOAD_RADIUS = 13;
```

1. Divide the world into square **cells** of `BOARD_CELL × BOARD_CELL` chunks. Cell `(cx, cz)` is centred on chunk `(cx × BOARD_CELL, cz × BOARD_CELL)`. The spawn chunk is `(0, 0)`.
2. **The spawn cell `(0,0)` has no board.** Only the neighbouring cells do.
3. The board's chunk is the cell centre plus a random shift of −2…+2 chunks on each axis:
   `jx = hash32(seed, cx, cz) % 5 − 2`, `jz = hash32(seed ^ 0x9E3779B9, cx, cz) % 5 − 2`.
   Neighbouring boards are then 31–39 chunks apart and the nearest board is 33–37 chunks from spawn.
4. **Which cells get a board:** list all cells except `(0,0)`, sort by **ring** `max(|cx|,|cz|)` and then by `hash32(seed ^ 0x51ED270B, cx, cz)` (random order inside a ring). Take the first `N` cells (`N` = number of messages). With 50 messages that is every cell of rings 1–3 (8 + 16 + 24 = 48) plus 2 random cells of ring 4. Cells beyond that have no board. Everything is computed once at startup into a `Map<cellKey, Board>`.
5. **Which message goes where, with no repeats:** shuffle the list of message ids once with a seeded Fisher–Yates shuffle, then give the i-th cell in the sorted list the i-th id. Each message therefore appears on exactly one board.
6. `seed` comes from the authenticated player's `player_profiles.world_seed` row in Supabase (created once as described in section 1.4). It stays consistent across browsers/devices. A development-only `?seed=123` override may be used for visual debugging; it must never overwrite the database seed or affect saved achievement identity.

```ts
const hash32 = (seed: number, a: number, b: number) => {
  let h = (seed ^ Math.imul(a, 374761393) ^ Math.imul(b, 668265263)) >>> 0;
  h = Math.imul(h ^ (h >>> 13), 1274126177) >>> 0;
  return (h ^ (h >>> 16)) >>> 0;
};
function mulberry32(a: number) { // small seeded PRNG
  return () => { a |= 0; a = (a + 0x6D2B79F5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296; };
}
```

**Checked by simulation** (2,000 random seeds, same algorithm in Python): 50 boards each time, all 50 messages used exactly once, no two boards in the same chunk, neighbouring boards 31.0–39.2 chunks apart, nearest board 33 chunks from spawn, farthest up to about 201 chunks from spawn. Write the same checks as a unit test (`src/world/boards.test.ts`) over 1,000 seeds.

### 2.2 How far is that in metres?
"30–40 chunks" depends on the game's chunk size. If chunks are 16 m (SPEC.md default), 35 chunks is 560 m and the farthest board is about 3.2 km from spawn. **On first run, print the chunk size and these distances and tell the user.** If it feels too far or too near, change `BOARD_CELL` (30–40) only.

### 2.3 Position and orientation
- World position = centre of the board's chunk plus a random offset of up to ±3 m (seeded), `y = terrain.heightAt(x, z)`.
- Yaw: the board **faces the spawn point**, so a player travelling outward sees the front first. `yaw = atan2(−x, −z)` (check the sign against the model's facing with a debug arrow).
- Hide grass blades in a 2 m radius around the board's posts. Reuse the "bite point" or exclusion uniform from the grass shader; do not add a second system.

### 2.4 Streaming
Create a board's mesh and texture only when the player is within `BOARD_LOAD_RADIUS` chunks, and dispose of it beyond `BOARD_UNLOAD_RADIUS` (dispose geometry, material and texture). At most one or two boards are loaded at any time. Never create 50 textures at startup.

### 3.2 Putting the text on the board (nội dung trên bảng)
Draw the message into a `<canvas>` and use it as a texture on the panel plane (`THREE.CanvasTexture`, `colorSpace = SRGBColorSpace`, anisotropy set to the renderer maximum, mipmaps on).

- Canvas size 1536 × 800 pixels for a 3.6 × 1.9 m panel (about 430 px per metre).
- **Font:** use one that fully supports Vietnamese. **Be Vietnam Pro** is a good choice (licence OFL-1.1, https://fontsource.org/fonts/be-vietnam-pro). Install with `npm i @fontsource/be-vietnam-pro` and import the weights needed. Check which subset files the package provides (the Vietnamese ones). Self-host the font; do not load it from a CDN at runtime.
- Before drawing, wait for the font: `await document.fonts.load('600 48px "Be Vietnam Pro"')`. Without this the first board is drawn in a fallback font without proper diacritics.
- Colours: dark panel `#2a1f1a`, warm cream text `#f3e6c8`, a thin lighter border. Add a small `emissive` map (same canvas, emissive intensity about 0.25 at night, 0 by day) so the text stays readable in the dark, like the glow on the reference board.

### 3.3 Text layout (auto-fit)
```ts
function drawMessage(ctx, text, w, h) {
  // 1. start at fontSize 64, line height = fontSize × 1.4 (Vietnamese diacritics need the room)
  // 2. wrap by words with ctx.measureText inside a width of w − 2×margin; honour \n
  // 3. if lines × lineHeight > h − 2×margin, reduce fontSize by 4 and repeat; minimum 30
  // 4. if it still does not fit at 30, cut the text and add "…" (and log a warning with the id)
  // 5. centre the block vertically; left-align the lines
}
```
Add a small "✓" mark (drawn as a path, not an emoji) in the panel corner when the message is already collected. **Never display a message id, discovery number, board number or sequence number anywhere on the physical board**, including the banner and panel.

### 3.4 Behaviour
- The board is static: no collision with grass or horse needed, except a simple cylinder collider on the posts so the horse does not walk through them (optional).
- Cast a shadow with the posts and frame only, not the panel.
- Fog and weather apply as usual. In rain, darken the wood by the existing `wetness` value.

## 4. Achievements (thành tựu)

### 4.1 Unlock rule
Every frame (or when the player's chunk changes), compare the player's chunk with the chunks of all boards. **When the horse enters a board's chunk, and that message is not yet collected, unlock it.** The board stands at the middle of the chunk, so the player is at most about 11 m from it when this happens. Use the player's chunk, not the board mesh being loaded, so the unlock also works while the mesh is still being created.

### 4.2 Supabase persistence and unlock reliability

- Store unlocks in `public.player_achievements` using `(user_id, message_id)` as the unique key. The database supplies `discovered_at`; the client never supplies or changes the discovery timestamp.
- When entering a board's chunk, if the message is not unlocked, insert `{ user_id, message_id }` once. Handle duplicate-key conflicts as an already-completed unlock (e.g. after reconnect or from another device). Prevent repeated concurrent requests while an insert is pending.
- **Only after a successful database insert** show the chime and new-discovery toast. If the insert fails due to network/auth error, show a small retry notice and allow the next entry/retry to save it; do not falsely announce a persisted achievement.
- On login and reload, query all of the player's achievements ordered by `discovered_at ASC, message_id ASC` for a deterministic discovery sequence. Keep an in-memory copy only while signed in; do not persist it in browser storage.
- Mark `read_at` when the user opens a discovered message for the first time. For a secure production implementation, prefer a dedicated server-side RPC that only sets `read_at` and leaves discovery data immutable.
- Options → "Reset thông điệp" requires confirmation and deletes **only the current user's** achievement rows. Because the SQL above deliberately has no client delete policy, provide a separate, explicitly reviewed owner-only reset RPC/policy in a future implementation if reset is required; until then **hide/disable Reset** rather than pretend it works. Do not delete the world seed.

### 4.3 Notification (toast)
On unlock, show a toast at the top-centre for 4 s (queue several if needed): the title "Đã tìm thấy một thông điệp" and "12 / 50" (progress count, not a board number), then the first 60 characters of the message with "…". It must never pause the game or steal keyboard focus. Fade in and out over 0.3 s.

### 4.4 The achievement board (bảng thành tựu)
- A button "Thông điệp" in the HUD (next to Options) and a key `J` open a panel.
- Header: "Thông điệp đã tìm thấy 12 / 50" with a thin progress bar.
- List discoveries in **oldest-first discovery order**, numbered **1, 2, 3, ...** using the position in the player’s discovered list (not `message_id`, board location, or global message order). If the player has found two, the panel shows exactly **1** and **2**. Each row shows that discovery number, the first line of text and the date. Click to read the full text. Locked slots are not listed; show only the remaining count. Numbers appear **only in this achievement panel**, never on the world boards.
- A small "mới" (new) dot on rows not yet opened, and on the HUD button until the panel is opened.
- Keyboard: Esc closes it. Mobile: full-width sheet.
- When all messages are found, show a final, gentler toast: "Bạn đã tìm thấy tất cả thông điệp." (The user may want to change this text; keep it in config.)

### 4.5 Sound for the unlock (âm thanh thành tựu)
The game is calm, so use a **soft bell-like chime**, not an arcade jingle. Keep it under 2 s, roughly as loud as the footsteps.

**Default (recommended): generate it in code.** No download, no licence, and every unlock can sound slightly different but always pleasant:

```ts
// 3 soft bell notes on a pentatonic scale, played as a short rising phrase
const SCALE = [523.25, 587.33, 659.25, 783.99, 880.0, 1046.5]; // C5 D5 E5 G5 A5 C6
function playChime(ctx: AudioContext, out: AudioNode, level = 0.25) {
  const start = ctx.currentTime + 0.02;
  const picks = [0, 1, 2].map(() => SCALE[Math.floor(Math.random() * SCALE.length)]).sort((a, b) => a - b);
  picks.forEach((f, i) => {
    const t = start + i * 0.16;
    for (const [mult, amp] of [[1, 1], [2.01, 0.35], [3.99, 0.12]] as const) { // bell-like partials
      const osc = ctx.createOscillator(), g = ctx.createGain();
      osc.type = 'sine'; osc.frequency.value = f * mult;
      g.gain.setValueAtTime(0, t);
      g.gain.linearRampToValueAtTime(level * amp, t + 0.012);
      g.gain.exponentialRampToValueAtTime(0.0001, t + 1.4);
      osc.connect(g).connect(out); osc.start(t); osc.stop(t + 1.5);
    }
  });
}
```
Route it through the `sfx` bus and add a little reverb (a short `ConvolverNode` or a 2-tap feedback delay) so it blends with the field. While it plays, lower the weather and night layers by about 3 dB for 1.5 s (duck), then restore them.

For the 1st, 10th, 25th and 50th discovery (by per-user unlock count), play a slightly longer version (4 notes, ending an octave higher).

## 5. Stamina (sức bền)

### 5.1 Rules
- `stamina` runs from 0 to 100 and **starts full**.
- **Galloping drains it** (`GALLOP_DRAIN`). Walking and standing do not drain it.
- **Stamina only comes back by eating.** While the eat state is active (E held, horse standing still on the ground), stamina rises by `EAT_RESTORE` per second. There is no passive regeneration by default (`IDLE_REGEN = 0`).
- When stamina reaches 0 the horse becomes **exhausted** (`exhausted = true`): the run key is ignored and the maximum speed is the walk speed. A running horse slows down smoothly over about 1 s; it does not stop instantly.
- To prevent flicker at the edge, the horse can gallop again only when `stamina ≥ RECOVER_THRESHOLD` (hysteresis). Set `RECOVER_THRESHOLD = 100` if the user wants the literal "only when the bar is full" rule.
- Jumping costs `JUMP_COST` (default 0, so it is off).

```ts
// src/config/stamina.ts — all numbers in one place
export const STAMINA = {
  max: 100,
  gallopDrain: 8,        // per second  -> a full bar gives 12.5 s of gallop (about 87 m at 7 m/s)
  eatRestore: 14,        // per second  -> an empty bar refills in about 7 s of eating
  idleRegen: 0,          // per second  -> 0 = only eating refills
  jumpCost: 0,
  recoverThreshold: 20,  // can gallop again from this level after being exhausted
  eatDelay: 0.5,         // seconds of eating before the bar starts to rise (head goes down first)
};
```

```ts
// each fixed update step
if (galloping) stamina -= gallopDrain * dt;
else if (eating && eatTimer > eatDelay) stamina += eatRestore * dt;
else if (idle) stamina += idleRegen * dt;
stamina = clamp(stamina, 0, max);
if (stamina <= 0) exhausted = true;
else if (exhausted && stamina >= recoverThreshold) exhausted = false;
canGallop = !exhausted;
```
With these numbers one cycle (12.5 s galloping plus 7 s eating) averages about 4.5 m/s, against 2 m/s walking. The numbers are starting points; the user can tune them.

### 5.2 Where it plugs in
- **Controller:** the maximum speed is `canGallop && runKey ? runSpeed : walkSpeed`, with the existing acceleration smoothing, slowed to about 1 s when stamina runs out.
- **Auto-wander:** the autopilot may choose to run only when stamina is above 50 %. If stamina is below 25 % and the horse is not eating, it immediately chooses an "eat" action (5–8 s, until stamina is at least 80 %). The horse looks after itself.
- **Eating:** reuse the existing eat state and the grass bite points. If the player is moving, nothing refills.
- **Audio:** play `horse_breath_1/2` (optional extras in the audio addendum) once when exhaustion starts, then every 3 s while the exhausted horse is moving; play the softer snort when `recoverThreshold` is reached. If those files are missing, skip silently.
- **Camera:** the FOV widening during a run (60 → 68) returns to normal when exhausted.
- **Weather:** none, unless the user later wants rain to slow recovery.

### 5.3 HUD
- A horizontal bar at bottom-left, above the "Controls" button, with a small horse-shoe or lightning icon and no number clutter (optionally the percentage on hover).
- Colour changes green → amber → red as it drops, **and** the bar's width and an icon state show the same information, so the meaning does not depend on colour alone.
- When exhausted: the bar pulses slowly and the text "Hết sức — giữ E để ăn cỏ" appears. When the player presses the run key while exhausted, the bar shakes once.
- When full and idle for 3 s the bar fades to 40 % opacity so it does not distract.
- Mobile: put it in the touch layout beside the Eat button.

## 6. Settings and persistence

Show logged-in account identity and a **Log out** action in Options. Supabase persists message content, world seed and discoveries per authenticated user. Stamina is not persisted and starts full on each visit. No browser storage is used for gameplay state. Reset progress is disabled unless a separately reviewed, user-scoped server operation is implemented (section 4.2).

## 8. Acceptance checks
- Unit test: for 1,000 seeds there are exactly N boards, each message id appears once, no two boards share a chunk, neighbouring boards are 31–39.2 chunks apart, and the nearest board is 33–37 chunks from spawn.
- Walking from spawn in a straight line, the first board appears after about 33–37 chunks. The printed distance in metres matches what the user expects (section 2.2).
- A board's text is fully readable from 8 m, has correct Vietnamese diacritics on the very first board shown, and never overflows the panel (test with a 20-character and a 280-character message).
- Entering a board's chunk plays the chime once, shows the toast once and adds the message to the log. Walking out and back in does nothing. Reloading or signing in on another device restores the same user’s discoveries and board placement from Supabase.
- Physical boards show no message or discovery numbers; after two discoveries the achievement panel displays rows numbered 1 and 2 (in discovery order), regardless of database ids. A second account sees separate progress. Failed inserts do not generate success toasts.
- Boards load and unload with no frame hitch above about 100 ms, and no more than two board textures exist at once.
- Stamina: holding the run key drains the bar; at 0 the horse slows to a walk within about 1 s and the run key does nothing; holding E refills the bar; the horse can gallop again once the recover threshold is reached; the HUD matches the state at all times.
- Auto-wander never gallops while stamina is under 50 % and goes to eat when it is under 25 %.

## 10. Thuật ngữ (glossary)

| Thuật ngữ (Vietnamese) | English definition |
|---|---|
| Sức bền (stamina) | A meter that is used up by running and refilled by eating |
| Thành tựu (achievement) | A reward or record for reaching a goal in the game |
| Ô lưới (cell) | A square group of chunks used to place one board |
| Hạt giống ngẫu nhiên (random seed) | A number that makes "random" results repeat exactly the same way |
| Kiệt sức (exhausted) | The state when stamina is zero and running is blocked |
| Độ trễ ngưỡng (hysteresis) | Using two different thresholds so a state does not flicker on and off |
| Kết cấu từ canvas (canvas texture) | An image drawn by code and used as a surface texture on a 3D object |
